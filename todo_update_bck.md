# Release Notes & Release Site (todo.md L46 + demande Pages)

## Résumé

Trois constats vérifiés dans le code, qui fixent le design :

1. **Le What's New de l'Update Manager est cassé, pas seulement manuel.** `ChangelogManager.parseMarkdown` attend `## Version X.Y.Z (YYYY-MM-DD)` + `- [NEW]` / `- [FIX]` / `- Breaking change:` (le vocabulaire de ses propres tests, `ChangelogManagerTest:34-40`), alors que `CHANGELOG.md` et `scripts/release/release-notes.sh` (qui en extrait la section brute) écrivent `## [X.Y.Z] — YYYY-MM-DD — …` + des groupes `### Added/Fixed`. La regex `##\s+(?:Version\s+)?([\d.]+)` ne matche jamais un `[` : **zéro entrée parsée → `Optional.empty()` → « No changelog available »**.
2. **`whats-new.mnd` est déjà le bon réacteur** : il lit `CHANGELOG.md`, produit un HTML déterministe (aucun timestamp), et sa paire `whatsNewRefresh` / `whatsNewCheck` (gate dans `repositoryChecks`) empêche déjà la dérive. Un second générateur de notes serait du dupliqué : **on ne le fait pas.**
3. `deploy-docs.yml` est le seul éditeur du site Pages, publie `documentation/**` **commité**, et guarderait explicitement la publication du Javadoc. Les rapports de tests sont donc générés hors repo (`build-gradle/`, git-ignorés) et ne peuvent être accumulés sur le site que via un stockage persistant.

Décision : **une source (`CHANGELOG.md`), un réacteur (`whats-new.mnd`), trois consommateurs** — le topic du Help Center (inchangé), l'archive Pages par version (nouvelle cible du même script), et l'Update Manager (qui lit le même document, sans artifact intermédiaire). Les rapports lourds vont sur Pages **et** en asset de la Release.

## 1. Update Manager : lire le vrai CHANGELOG (aucun second fichier de notes)

- `update-manager/…/changelog/ChangelogManager.java` : apprendre le vocabulaire Keep a Changelog **en plus** du vocabulaire legacy (celui des tests existants et de l'asset `changelog.md` déjà publié par les releases passées) :
    - en-tête `## [X.Y.Z] — date — …` → version `X.Y.Z` (les suffixes `-dev` / `-rc.1` sont gardés tels que写的, `getEntry` compare la version de base d'abord, puis l'en-tête complet) ; `[Unreleased]` n'est jamais soluble par `getEntry(version)` mais apparaît dans `toHtml()` ;
    - groupes `### Added|Changed|Deprecated|Removed|Fixed|Security` → respectivement `features`, `changes`, `breaking`, `breaking`, `fixes`, `fixes` ; une puce sans groupe reste `changes` ;
    - le markdown inline déjà écrit dans le changelog (`**bold**`, `` `code` ``, liens) est rendu en spans HTML, pas affiché brut ;
    - aucune modification des signatures publiques existantes (`fromMarkdown`, `getEntryHtml`, `toHtml`, `ChangelogEntry`), donc `UpdateService` / `UpdatePresenter` / `ChangelogDialog` ne bougent pas.
- Le bundle doit réellement contenir le document que ce parser lit :
    - `lg3d-core/build.gradle` `releaseBundle` : `from(rootProject.file('CHANGELOG.md')) { rename { 'changelog.md' } }` à la racine de l'archive (à côté de `lg3d.sh` / `README.txt` / `VERSION`) ;
    - tâche `releaseLauncher` : ajouter `-Dupdate.changelog.path="${HERE}/changelog.md"` à la ligne `exec` de `lg3d.sh`, et, **si** la config de l'Update Manager ne résout pas les propriétés système (à vérifier dans `UpdateService`/son `Config`), étendre `getLocalChangelogPath()` pour chercher aussi à la racine d'installation (`InstallLocation`) plutôt que seulement dans `user.dir`.
- Le chemin distant (`version.json` → `changelog` → asset `changelog.md` produit par `release-notes.sh`) devient fonctionnel sans changement côté workflow : c'est déjà une section brute du CHANGELOG, que le nouveau parser lit.

## 2. `whats-new.mnd` : seconde cible = l'archive Pages, même réacteur

- Le script garde ses fonctions `plain/markup/inline/headline/sectionsOf/entriesOf/tree/render` ; `render()` est paramétré (head/tail du document : CSS `lg3d-help.css` pour le topic Help Center, `documentation/…` CSS de site pour les pages Pages) — **pas de copier-coller de la logique de rendu**.
- Nouvelles cibles commitées, une par version publiée du CHANGELOG (9 en-têtes `## [` aujourd'hui, dont `[Unreleased]` → 8 pages) :
    - `documentation/releases/<version>.html` — la section de cette version, seule ;
    - `documentation/releases/index.html` — la liste des versions (une ligne par page, avec date et titre de section) + lien vers la Release GitHub correspondante `https://github.com/landrevillejf/ProjectLookingGlass/releases/tag/v<version>` ;
    - chaque page porte le même marqueur « generated by scripts/mandela/whats-new.mnd from CHANGELOG.md — do not edit » et un lien retour vers `documentation/index.html`.
- Le gate `whatsNewCheck` est étendu (un seul script, une seule gate) : il compare **byte à byte** le topic du Help Center **et** chaque page commitée de `documentation/releases/` au rendu en mémoire ; une page absente ou périmée échoue, avec le message d'une seule instruction (pas deux `:` dans le message, sinon le CLI tronque la ligne). Une version présente dans le CHANGELOG mais sans page = finding ; une page sans version dans le CHANGELOG = finding (la page orpheline doit être supprimée).
- Gradle (`lg3d-mandela/build.gradle`) : `whatsNewRefresh` écrit les trois sorts (topic + pages + index) ; `repositoryChecks` garde les mêmes huit gates (aucune nouvelle gate, donc `scripts-hygiene.mnd` et le README des scripts ne gagnent qu'une ligne de description pour `whats-new.mnd`, mise à jour du paragraphe « the eight gates » si l'inventaire change).
- Portail Pages : une carte « Releases » dans `documentation/index.html` (et son reflet `fr/`) pointant `releases/index.html`, pour que les pages ne soient pas atteignables uniquement par lien profond.

## 3. Rapports de tests par release : Pages **et** asset de Release

Nouveau workflow `.github/workflows/release-reports.yml`, `on: release: types: [published]` + `workflow_dispatch` (tag en entrée), **jamais** déclenché par une PR :

1. checkout du tag (`fetch-depth: 0`), JDK 21, `JAVA_HOME` géré par `setup-java`.
2. `./gradlew test jacocoTestReport jacocoTestCoverageVerification :lg3d-mandela:pitest :lg3d-mandela:repositoryChecks --continue` (rapports dans `<module>/build-gradle/reports/…`).
3. **Pages** : arbre persistant `releases/<version>/reports/{junit,jacoco,pitest,cucumber}/` + `releases/<version>/index.html` (la page de release générée au point 4, avec les rapports en liens relatifs), poussé sur une branche orpheline dédiée `site-releases` (additif, une copie `git worktree` ; `--force` interdit, on empile les commits). C'est la storage branch que `deploy-docs.yml` matérialise ensuite.
4. Page de release avec les chiffres : le workflow assemble `releases/<version>/index.html` à partir de la page commitée `documentation/releases/<version>.html` (réacteur Mandela, donc jamais périmée) en y ajoutant l'en-tête « test reports » et les liens vers l'arbre de rapports ; les liens sortants relatifs ne peuvent pas casser les gates puisque l'arbre généré n'est jamais commité.
5. **Asset** : `reports-<version>.zip` (les mêmes quatre arbres) + `changelog.md` (déjà publié) attachés à la Release via `gh release upload`, pour que le rapport survive à une reconstruction du site.

## 4. `deploy-docs.yml` : un seul éditeur, qui accumule

- Étape « Check out the release archive » : `git fetch origin site-releases` puis extraction de `releases/` vers `_site/releases/` (si la branche n'existe pas encore, on continue sans cette section — le site ne doit jamais rouges pour ça).
- L'existing guard « API reference must not be committed » est conservé tel quel ; rien de généré n'entre dans `documentation/**`.
- Le `paths:` du déclencheur garde `documentation/**` ; le workflow `release-reports.yml` termine par un `workflow_dispatch` de `Deploy Documentation to GitHub Pages` (ou un push vide sous `documentation/` est évité : on utilise `actions/workflows/run` du job existant) pour que la nouvelle archive soit publiée dans la foulée.

## 5. Tests

- `ChangelogManagerTest` : nouveaux cas sur le vocabulaire réel (section `[1.68.0] — 2026-10-11 — …` avec `### Added/Fixed/Breaking…`), sur `[Unreleased]` qui ne répond pas à `getEntry`, sur l'absence de regression legacy, et sur le fait qu'une section du **vrai** CHANGELOG (un extrait fidèle, inline, pas de lecture du repo depuis le module) produit ≥ 1 entrée.
- Gate auto-testée : `ShippedScriptsTest` (lg3d-mandela) compile déjà tous les scripts de `scripts/mandela/` → le `whats-new.mnd` étendu est couvert ; ajout de cas pour `sectionsOf`/le mapping de groupes si la suite le permet sans I/O.
- `repositoryChecks` passe avec les nouvelles pages commitées (htmlLinksCheck audite `documentation/**`, donc les liens des pages + du portail doivent résoudre ; docLinksCheck audite le markdown).
- Aucun test n'ouvre le workflow : la vérification du pipeline est faite par un run `workflow_dispatch` manuel en mode sec (le user ne demande pas de release).

## 6. Documentation et hygiene

- `AGENTS.md` : liste des fichiers générés (ajouter `documentation/releases/*.html`), la gate `whatsNewCheck` décrite comme couvrant topic **et** archive, et la note « les rapports de release sont publiés par `release-reports.yml`, jamais commités ».
- `scripts/mandela/README.md` :的双 sorties de `whats-new.mnd` et leur gate.
- `documentation/README.md` : ce que la branche `site-releases` stocke et pourquoi le Javadoc ne sort toujours pas.
- `CHANGELOG.md` : entrées Added (archive Pages + rapports) et Fixed (le parser qui ne reconnaissait pas le propre format du repo) dans le même PR, puis `./gradlew :lg3d-mandela:whatsNewRefresh` (qui régénère aussi les pages) — une seule PR, gate `whatsNewCheck` verte.

## 7. Hypothèses et non-objectifs

- **Aucune release n'est coupée ni publiée** par ce travail : `make-release.sh` reste le seul chemin de cut, sur feu vert explicite (règle existante). Le point 3 est vérifié par `workflow_dispatch`, pas par un tag.
- Le Javadoc ne monte toujours pas sur Pages (guard existant conservé).
- PIT reste limité à `lg3d-mandela` (seul module configuré) ; le zip et la page n'affichent un rapport PIT que pour ce module, et l'index le dit clairement plutôt que de simuler une couverture PIT globale.
- Les pages d'archive sont commitées (8 fichiers, régénérables et comparés par la gate) : c'est le prix du « gates sur la page » choisi, et c'est ce qui rend le lien du portail vérifiable par `htmlLinksCheck`.
