## Key components

- **Tetris** — entry point; installs the hosted Metal LAF and shows the window.
- **TetrisPanel** — the Swing surface: board, sidebar (score/level/lines, next
  piece, Start/Pause/Settings, a five-button mouse control pad and the key
  legend); owns the fall timer, the keyboard and the turn-to-sound mapping.
- **TetrisBoard** — the custom-painted well; focusable and the only
  `KeyListener`, because that is the one keyboard path both desktops share.
- **TetrisEngine** — the game state machine (well grid, piece, lock, line
  clears, scoring, levels). No AWT beyond `Color`, no Swing, no timer — fully
  headless-testable, and every rule question is answerable through it.
- **Tetromino** — the seven pieces, their rotations and their colours.
- **TetrisSettings** — the player's three choices over `java.util.prefs`.
- **audio/TetrisAudio** — lazy Java Sound playback; degrades to silence.

## Roles

- **Architect** — The reverse of the four [`games`](../../../../../../../../../lg3d-incubator/src/classes/org/jdesktop/lg3d/apps/games/AGENTS.md)
  apps in the incubator: those were written as native 3D and later given a Swing
  panel, this one was written as plain Swing and is *hosted* on a `SwingNode` by
  `TitledSwingWindow`. Consume `lg3d-core` (`TitledSwingWindow`, `SwingNode`),
  never re-implement window plumbing. Keep `TetrisEngine` free of Swing and of
  any timer so it stays headless-testable; the panel owns the clock.
  Because the same class must be reachable from the 2D desktop, `Tetris` (the
  wrapper's own class name) is the key in `Desktop2DAppRegistry.PANEL_APPS` and
  `TetrisPanel` the value — the panel needs a no-arg constructor.
- **Engineer / Developer** — Follow the core UI/UX rulebook: SwingNode paints
  **offscreen with no layout pass**, so the panel uses explicit preferred sizes
  (`TetrisPanel.WIDTH_PX` / `HEIGHT_PX`) and the board paints itself in
  `paintComponent`; hop to the EDT from lg3d listeners; `installHostedLookAndFeel()`
  runs **before** the panel is built (Synth widgets NPE under SwingNode capture).
  **Input is a `KeyListener` on the focusable board**, not an input map:
  `SwingNodeRenderer` redispatches real `KeyEvent`s at a component, and
  `WHEN_IN_FOCUSED_WINDOW` never fires there. Sidebar buttons are
  `setFocusable(false)` so the board keeps focus and the keys.
  Sound loads **lazily** and may never throw — a machine with no mixer gets a
  silent, playable game. Clips are bundled beside the sources at
  `org/jdesktop/lg3d/apps/games/tetris/resources/sounds/` by the `lg3d-apps`
  resource source set; adding an `Effect` without shipping its file is silent
  forever, so `TetrisAudioTest` gates the two sets against each other.
  Jogamp packages only; nothing here may load a Java 3D class.
- **QA** — 51 headless JUnit 5 cases in `src/test/java/.../games/tetris/`:
  `TetrisEngineTest` (every rule — steps, rotation, lock, one and four line
  clears, level ramp, speed clamp, game over — driven by `showing(int)`, an
  engine whose `Random.nextInt` is pinned so the piece sequence is deterministic
  without seed hunting), `TetrisPanelTest` (construction, geometry, keys reaching
  the engine, every state painting), `TetrominoTest`, `TetrisSettingsTest` and
  `TetrisAudioTest`. Both settings tests build over a **unique throwaway
  preferences node** (`Preferences.userRoot().node("/lg3d/…-test/" + UUID)` +
  `removeNode()` in `@AfterEach`) — the test JVM does not isolate
  `java.util.prefs`, so a run must never touch the player's real choices.
  `Desktop2DAppRegistryTest.tetrisIsHostedPanel` asserts the command resolves.
  The modal settings dialog is not exercised: `JOptionPane` needs a window and a
  headless JVM has none. Verify the 3D surface with the in-JVM probe + internal
  screencapture (`lg3d-core/lgscreen-*.png`).
- **Business Analyst** — The Games group's fifth entry and the first written for
  both desktops at once rather than ported into them. It ships ~1.1 MB of WAV
  clips and deliberately **not** the 33 MB original victory jingle: a released
  jar is weight a user downloads to play a game.
- **Functional Analyst** — Spec user-visible function: falling pieces, rotate /
  move / soft drop / hard drop (each with a key *and* a control-pad button),
  levels that speed the fall every ten lines, scoring (40/100/300/1200 × level),
  pause, and the three settings (sound, volume, start speed). "At rest" and
  "game over" are different states — a reset board must not claim the player
  lost (`TetrisEngine.atRest()` is why), and `Enter` must never restart a run in
  progress.
- **Project Manager** — Commit scope `lg3d-apps` for the app, plus the two
  side-effects that are easy to mis-file: `Desktop2DAppRegistry` in `lg3d-core`
  and the generated icon in `lg3d-art` / `lg3d-core`. Say so in the PR. Done =
  build + `:lg3d-mandela:repositoryChecks` + `:lg3d-core:runtimeResources` + a
  desktop capture of the window in play.
- **UI/UX (3D & 2D)** — One panel, two hosts: the glassy `TitledSwingWindow`
  frame on the 3D desktop, an MDI internal frame on the 2D desktop. The board is
  custom-painted (a `CELL_PX` grid, the ghost drop target, the PAUSED / GAME
  OVER overlays drawn in-panel), so there is no sprite asset to lose. Every
  in-window string is drawn by this panel itself — the scoreboard captions, the
  control pad, the legend and the two overlays — and none of it is painted from
  an image, so a layout change is a code change and never a re-exported PNG.
  The **Settings** form is a `JOptionPane` confirm dialog parented to this panel
  — the same choice 47 other hosted `lg3d-apps` panels make
  (`FileManagerPanel`, `TaskManagerPanel`, the Control Center panels). It is
  capturable rather than a leak: `SwingNodeWindowCapture` exists precisely to
  capture a `JOptionPane` / `JFileChooser` / `JDialog` opened by a hosted panel,
  parking the real window off-screen and painting it as a centred overlay into
  the node's texture with input routed back to it — its own javadoc records that
  "Modal semantics are preserved because a modal dialog runs its own secondary
  EDT loop, which processes the events the node's renderer dispatches on the
  EDT". Parenting the dialog to the panel is what makes the owner chain
  attribute it to *this* node, so one code path serves the in-scene overlay on
  the 3D desktop and an ordinary dialog on the 2D one; a dialog with no owner
  would land on whichever node the pointer last entered.
  The sidebar labels are plain literals, not `Messages.tr()` lookups: like most
  of `lg3d-apps` they are unbundled English today, and translating them is an
  edit to `lg3d-core`'s shell bundle (`i18n-keys.mnd` gates the keys a source
  *does* ask for), not a change to this package.

## Communication & coherence

Single source of truth: this file (app) → module `AGENTS.md` → core UI/UX
rulebook → root `AGENTS.md`. On conflict the higher file wins; fix here in the
same PR. Every PR states the surface (SwingNode + PANEL_APPS), the descriptor
change (if any), and the capture/log evidence.

## Commit / PR

Conventional Commit scope `lg3d-apps` (or `agents` for this file); imperative
subject ≤ 50 chars; add a `CHANGELOG.md` bullet under `[Unreleased]` and run
`./gradlew :lg3d-mandela:whatsNewRefresh` in the same PR; no version bump. Stage
only intended paths (never `git add -A`).
